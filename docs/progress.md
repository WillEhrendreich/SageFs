# What SageFs has become, and what it means for you

I kept describing SageFs as a list of features, and a list of features doesn't tell you what it's like to sit down with it. So this page goes by time instead. Each stretch says what you had when it started, what you have now, and then walks through the changes one at a time: what it was like before, what it's like now, why you'd care, a link to the code that does it, and what's still rough.

If you only read one thing: F# Interactive is amazing. Type an expression, get the answer, no build. SageFs is FSI underneath, and I use FSI all day. But on a real project it has always made you do the work. You load the project yourself. You rebuild to find out if one function is right. You run `dotnet test` and wait. A web app means stop, build, start. SageFs is what happens when the REPL does that work for you, and over the last seven months it went from a daemon that held an FSI session to this:

- **Your project is already loaded, and "Ready" means it.** A session that loaded nothing says so, with a reason, instead of showing green.
- **You edit a function and the tests that reach it re-run**, saved or not. A body-only edit like `a + b` to `a - b` can't select zero tests and read green anymore.
- **You save a file and the running app serves the new code**, with the state you didn't touch still there. A hot reload only says "live" after SageFs has watched the new code run, and if it never ran you get "never entered", with the names.
- **Your pinned packages can't fight SageFs's.** Every session runs in its own host process, on the .NET your project needs.
- **When something breaks it tells you what and why.** A failed rebuild keeps the old worker serving the last good build. A dead worker leaves a log. A daemon log can't eat your disk.
- **Your agent works in the same session you do.** It runs your tests through `run_tests` and gets a receipt, so a pass left over from an earlier run never counts. It waits for a warming session instead of sleeping and polling.
- **You can leave the daemon running.** It doesn't follow symlink loops into the weeds, it watches machine memory and sheds work with a reason, and pages that aren't its own can't make it run F# as you.

None of that is finished, and every entry below says where it stops. I'd rather you hear it from me than find it out at 11pm.

## How to read this

The windows run newest first. Every claim links to the code at [`bba42706`](https://github.com/WillEhrendreich/SageFs/commit/bba42706), the commit for release v0.6.868, so the link keeps pointing at what I looked at even after the file moves on. Where a feature was later removed, I link the commit instead. Commit counts are by author date on `master`. A number that came from a commit message and that I didn't re-run says so. If you find something here that's wrong, open an issue, or tell me in Discord. I'd rather know.

## The stretch where SageFs stopped saying "fine" when it wasn't (2026-09-27 to 2026-09-30, 211 commits, v0.6.836 to v0.6.868)

At the start of this stretch a hot reload could tell you "Hot reloaded 1 of 1" while your running app went right on doing the old thing, a failed rebuild looked exactly like one that hadn't finished, a dead worker took its reason with it, and one pending Task bound at top level could freeze your session for good. By the end, SageFs waits to see the new code actually run before it says a patch is live, tells you when a rebuild failed and why, keeps real log files for the daemon and for every worker, goes Degraded when something underneath is stuck, and an agent can run your tests and get a receipt for that run instead of reaching for `dotnet test`. Most of it landed on the 30th (191 of the 211 commits on master), driven by dogfooding the tool on itself and by running cheap models through a first session to see where they tripped.

### A hot reload only says "live" once the new code has been seen running
Before: a save re-pointed the old function at the new body and SageFs said "Patched". If your caller had the function inlined, it kept running its own copy of the old body, the page served the old result, and every signal read as success.
Now: a save lands as "patch pending", the page refreshes, and the patch turns into "patched" only after every changed function has actually run. If 10 seconds pass and some changed function was never called, you get "never entered", naming the ones that didn't run. The same verdict shows up in `get_session_status` as `lastReload`, in the dashboard, and as a push notification to your agent, with a closed set of outcomes (patched, restarted, kept-a-value, didn't compile) instead of a bare "reloaded".
Why it matters: when your edit doesn't show up, you now learn whether the code ran or the app never reached it, instead of staring at an old page and wondering.
Evidence: [the decision, written without a clock or IO](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/PatchConfirmation.fs#L1-L22), [the events you see](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/DevReload.fs#L250-L263), [the bound](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Timeouts.fs#L357), [real-app journeys on net10 and net11](https://github.com/WillEhrendreich/SageFs/commit/53d90ee4)
Rough edges: a helper nothing calls ends as "never entered" after the bound, which is correct but will read like a warning until you know why, and mutable bindings are not probed.

### Saving a file in an app you started with run_app now restarts it and says why
Before: every save to an app started by `run_app` was a silent no-op reported as a success. The patch went into the FSI host's copy of the function, the app lives in the worker, and the ticker sample kept printing the old text.
Now: that kind of change becomes a restart with a reason attached ("renderLine changed, and this app runs in the worker, where an in-place patch cannot reach it"). In the ticker the new text shows up about 6 seconds later. An app you started from FSI or an init script keeps its in-place patch.
Why it matters: the first thing a new user tries is edit, save, look, and for run_app apps that used to do nothing at all.
Evidence: [the placement rule](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/ReloadPlanning.fs#L1160-L1193), [the commit with the red-then-green run](https://github.com/WillEhrendreich/SageFs/commit/71f21e2f)
Rough edges: it is a restart, not an instant patch, and state survives it only where your app registered it.

### A failed rebuild or a dead worker now says what happened
Before: `hard_reset_fsi_session` with `rebuild=true` answered "initiated", the old worker kept serving, and a build that failed left no log line and no status field. On the ticker sample that meant a save could never reach new code and nobody was told. A worker that died had its first 20 lines of stderr reported, which is startup noise, not the reason. And if `dotnet` wasn't on the daemon's PATH, the rebuild threw on a pool thread and ended the whole daemon process.
Now: `get_session_status` carries `lastRestart` (what the last rebuild did, and the message), and the daemon records it for rebuilds started from the dashboard and live testing too, not only from the MCP tool. A dead worker reports the last 20 of the last 200 stderr lines. A rebuild that can't start returns a failure that names the directory. A replacement worker that comes up with a bad transport leaves the old one serving instead of leaving you Faulted next to a healthy worker. And the wait after a rebuild is one await on the session manager, not a poll every 50 then 250 ms for up to 30 seconds, so a faulted session fails at once with the manager's reason.
Why it matters: when a reset doesn't take, you find out which of build failed, worker died or swap refused, and you find out right away.
Evidence: [lastRestart in the status payload](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/SessionStatusPayload.fs#L96-L122), [the bounded stderr tail](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/TailBuffer.fs#L62-L85), [the rebuild that used to end the process](https://github.com/WillEhrendreich/SageFs/commit/28238c25), [the single-await wait](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/RebuildReadyWait.fs#L1-L40)
Rough edges: the bad-transport swap fix is tested against fakes, the commit says no real worker process was used.

### Workers have real log files and the daemon log can't eat your disk
Before: every worker's logging had zero sinks, so project-load failures, "Hot reload:" lines and the fallback to manual fsproj parsing were dropped, and the only way to see why a session came up degraded was to spawn the host by hand with redirects. The daemon log was worse: 7 of 20 daily files sat at exactly 1 GiB (10.3 GiB in total) and stopped writing mid-day, because the library's size roll was off and the noisy "Request starting" lines weren't being filtered.
Now: each worker writes `<data dir>/workers/<session>.log`, capped at 4 MiB with one rolled generation. The daemon log rolls by day and by size at 50 MB, 7 files at most (350 MB, against a library default of 1 GiB for 31 files), follows `SAGEFS_DATA_DIR`, and its path is in `/api/daemon-info`. An unexpected 500 is logged with its stack and the response carries a request id you can match to it.
Why it matters: "why is my session degraded" now has a file to open, and a daemon left running for weeks doesn't fill the drive.
Evidence: [the worker log writer](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/WorkerLogFile.fs#L40-L56), [installed at worker start](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Host/Program.fs#L40-L51), [the daemon log bounds](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/DaemonState.fs#L82-L99)
Rough edges: the commit that adds the path to `/api/daemon-info` leaves `sagefs status` and `get_daemon_status` for a follow-up, and I did not check whether that landed.

### Health goes Degraded when the session manager is stuck or your build can't hot reload
Before: if one command blocked the session manager's loop, status reads kept answering from a snapshot and everything looked fine while every caller that needed the manager hung. Separately, a project someone had built with optimizations could have a function inlined into its callers, so a hot-reload patch quietly never reached them.
Now: a watchdog thread notices a command that has held the loop for 30 seconds, raises an alarm, and `/health` and the dashboard go Degraded with the reason. A session whose project assembly was built optimized is Degraded too, with the remedy (`hard_reset_fsi_session rebuild=true`). Restart delays also get jitter, so a dozen workers that die together (a sleep, an OOM kill) don't all retry on the same tick.
Why it matters: a daemon that is stuck or a session that can't honor a patch now says so where you are already looking.
Evidence: [the supervisor alarms](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/SupervisorWatchdog.fs#L18-L31), [how it degrades overall health](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/DaemonHealth.fs#L115-L123), [the optimized-build reason](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/SessionHealth.fs#L89-L96)
Rough edges: a build whose optimization state can't be read is deliberately silent, so absence of the warning is not proof.

### Binding a pending Task at top level no longer freezes your session
Before: `let t = client.GetAsync url` hung the next eval for good. The live-values pass reads every public property of a class value after each eval on the eval thread, a Task is a class, and reading `Task.Result` waits for it. The worker sat idle and nothing answered.
Now: Tasks, ValueTasks and Lazy values are shown by their state, and `Result` is only read once the task has finished, so looking at a value never waits on it or runs your factory. Any other getter that blocks gets a 1 second budget per binding and shows as unreadable. A first version of that guard started a thread per binding and cost 80x on the hot path (0.30 ms to 24.65 ms for 200 bindings); the shipped version uses one walker thread per pass and costs 0.40 ms against 0.35 ms unguarded.
Why it matters: the ordinary thing a person types while poking at an HTTP client can't brick the REPL anymore.
Evidence: [the Task and Lazy handling](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/LiveValueTree.fs#L130-L139), [the per-binding budget](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/LiveValueTree.fs#L562-L568), [the numbers](https://github.com/WillEhrendreich/SageFs/commit/c77e928a)
Rough edges: a getter that really does block shows as unreadable for as long as it blocks, which is the right call but not a fix for your getter.

### Agents can run your tests through SageFs and get a receipt
Before: there was no run-tests tool, so agents reached for `dotnet test`, a second engine whose answers can disagree with the dashboard and `list_tests`. Two tool descriptions even pointed at tools that don't exist (`run_project_tests`, `run_tests`), and in an onboarding trial the agents that followed them ran `dotnet test` on an Expecto exe project five times in one run and found nothing.
Now: `run_tests` dispatches the same request the editors and dashboard send and reads the engine's own record of it back. A refusal says why (session not trusted, nothing discovered, filter matches nothing). A finished run is AllPassed, SomeFailed or Incomplete, with one line per requested test saying what happened to it in this run, and a pass from an earlier run is never counted. If the wait runs out you get a `receipt_id` to call again with. A test reads the tool catalog and fails the build if any description names a tool that isn't registered. The server has 61 tools at this point.
Why it matters: "did my tests pass" has one answer, from the same engine you see in the dashboard, and an agent can't mistake "nothing ran" for green.
Evidence: [the tool and its description](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpTools.fs#L2113-L2130), [the receipt types](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/TestRunReceipt.fs#L12-L30), [the catalog check that caught the dangling names](https://github.com/WillEhrendreich/SageFs/commit/a43d5d5c)
Rough edges: the same morning's docs said "There is no run_tests tool, on purpose"; the tool arrived hours later, so older notes may still say that.

### Agents can wait for a warming session instead of sleeping
Before: weak models in a trial couldn't wait for a session to warm up, so they slept or polled: two or three sleeps a run and 19 to 28 SageFs calls.
Now: `get_session_status` takes `wait_seconds` (clamped to 0 to 60). A session that is Starting, Building or Restarting parks the call on the manager's event-driven wait. The reply has a `wait` field saying how it ended: NotNeeded, BecameReady, Faulted or TimedOut. A Ready, Faulted or Stopped session never waits. The "still warming" messages now point at it instead of "poll every 5-10s".
Why it matters: your agent's first minute stops being a pile of sleep commands.
Evidence: [the tool parameter](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpTools.fs#L796-L810), [the cap](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Timeouts.fs#L104)
Rough edges: the commit says it was tested against a fake wait, not a live daemon parking on the real manager.

### The agent tools stopped doing quietly wrong things
Before: `send_fsharp_code` kept the last result per session and snippet, and if you sent the same code twice within 2 seconds it returned the old result without running it, so `counter <- counter + 1` sent twice ran once and the second reply said `val it: int = 1`. It also cached failures. `switch_workflow` tried to create a second session in the same directory and was refused by the duplicate guard. Several descriptions said "pass session_id" on tools that had no such parameter. A refused call said "session is not Ready, wait" when the real problem was that no session matched. A file that opens with `namespace` or a dotted `module` got a parser error that pointed at nothing.
Now: every submission runs, `switch_workflow` restarts the same session in place and keeps its id, five tools take an optional `session_id`, a routing miss gives the routing message with a create hint, a nonexistent directory is named, and a namespace or module line gets told to send the file with `file_path` and `eval_mode=file`.
Why it matters: an agent that double-submits sees the effect twice, plainly, and the error text tells it what to try next.
Evidence: [the dedup removal](https://github.com/WillEhrendreich/SageFs/commit/ca36d0de), [the declaration hint](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/EvalPreflight.fs#L30-L45), [switch_workflow through the manager](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/Mcp.fs#L2348)
Rough edges: none I could find beyond the usual one, which is that these were all found by trial runs, so there are probably more of them.

### The .NET 10 tool actually works, and it has its own test tier
Before: the unit suite only ran on net11, so a bug that exists only on .NET 10 was invisible. .NET 10's System.Text.Json throws on an F# union where .NET 11 writes it, and `get_session_status` put a union in its payload, so on the net10 tool, the one most people install, the first tool the skill tells an agent to call failed for every session.
Now: the status target is a plain `{kind, path}`, and the default suite runs on net10 as its own tier (`default-net10`) with its own row in the trust report. The first net10 run errored 24 tests, 21 of them through `get_session_status`. A single `SageFs.Json` facade now owns serialization with golden-text tests in both tiers; it replaced sixteen separate options objects that each decided for themselves.
Why it matters: what you install from NuGet on .NET 10 is now the thing that gets tested.
Evidence: [the wire shape](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/SessionProjectTarget.fs#L120), [the net10 tier](https://github.com/WillEhrendreich/SageFs/blob/bba42706/ci-pipeline.fsx#L690-L695), [the JSON facade](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Json.fs#L70-L80)
Rough edges: the integration, mutation and browser tiers still run on net11 only.

### First run on a fresh Linux box got friendlier
Before: `sagefs status` with nothing running printed two warning lines about a refused connection before saying so. A daemon started by `claude mcp add sagefs -- sagefs mcp` on the default port was tied to that one agent and died seconds after it exited, taking the dashboard and other agents' sessions with it. Your first `git status` showed an untracked `.SageFs/warmup-replay-cache.json` full of this machine's NuGet paths. A bare session logged a red "no source files for this project" failure. And a daemon started in `$HOME` would hand `$HOME` out as a watch root and spend an inotify watch on every directory under it.
Now: a refused connection is the expected answer and prints nothing extra, plus how to start a daemon and the right `claude mcp add` command. The home-port daemon has no owner, so it outlives the agent. The cache writes a `.gitignore` for itself only, leaving `config.fsx` and `init.fsx` committable. A bare session warms up quietly. A watch root that is the home directory or above it is refused, reported to `/health` with a hint to open the session in a project directory. There is a systemd user unit in `contrib/systemd`.
Why it matters: the first ten minutes with the tool stop having small unexplained messes in them.
Evidence: [the probe classifier](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/DaemonState.fs#L258-L267), [who owns the daemon](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpStdioBridge.fs#L264-L274), [the refused watch root](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/FileWatcher.fs#L343-L375), [the cache ignoring itself](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/WarmupReplayCache.fs#L270-L282)
Rough edges: the service unit is Linux only, and nothing in this stretch covers Windows or macOS login startup.

### A session only shows its own tests, and the dashboard stopped dropping streams
Before: on 0.6.850 a new session's `list_tests` returned another, stopped session's file paths under a deleted directory, because test locations were shared across sessions. Separately, about 1 dashboard page load in 80 stopped streaming under a name it never chose: the page id is 8 hex digits, and when it looked like `2352e570` the router's number parser turned it into `Infinity`. The friction panel you asked for also vanished on a reconnect.
Now: a session lists only tests and paths under its own working directory and projects, and stopped sessions are retired from the active pointer. The stream reads the page id as text (measured: 2,517 of 200,000 minted ids were misread, 1.26%), and a page's choices belong to the page, not to whichever connection is open.
Why it matters: you see your own tests in your own session, and a dashboard page does what you asked for every time, not 79 times in 80.
Evidence: [per-session attribution](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/SessionTestAttribution.fs#L38-L48), [the page id fix](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/Dashboard.fs#L1982-L1998), [the reconnect race](https://github.com/WillEhrendreich/SageFs/commit/574be30a)
Rough edges: the cross-session fix changes no stored format, and I did not check it against a live multi-session daemon.

### Changing a record's shape can keep your live value, if your app registered it
Before: a type change in a hot-reload save was priced as a restart. The reasoning in the docs was that a no-build plan leaves the new type with no compiled form, so there is nothing to construct.
Now: that premise turned out to be wrong, because FSI compiles a patched type at runtime and it is a real type the moment the patch lands. A record constructor takes one argument per field, so the migration builds the new record from the old values by field name, defaults a field the edit added only when that is safe, and refuses (naming the type) instead of inventing a value for something like an added `Map`. This was reachable on the 27th, when it stopped being dead code.
Why it matters: adding a field to a record you're iterating on doesn't have to throw away the state you built up to test it.
Evidence: [the executor](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/ShapeMigration.fs#L76-L100), [the boundary hook it reads](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/RestartBoundaries.fs#L70-L82), [the commit with the live transcript](https://github.com/WillEhrendreich/SageFs/commit/67af6421)
Rough edges: it is opt-in, your app has to register a boundary that hands over the live value, and records of other field kinds than int, string and bool fall to "no rule" and rebuild.

## The stretch where the daemon stopped eating the machine and started saying what was wrong (2026-09-22 to 2026-09-26, 314 commits, v0.6.803 to v0.6.835)

At the start of this stretch you could point SageFs at a repo, leave the daemon running overnight, and wake up to a 62GB box with the daemon sitting on 55GB of it while every session said Ready and /health said Healthy. By the end you could do the same thing and the daemon watches its own memory against the machine, refuses new work with a reason when it is short, and tells you which signal broke when something does. You could also point it at the F# compiler repo itself and get a session instead of a 20 minute spinner, edit a plain `let` value in a running app and see it land without a restart (when SageFs can prove nothing copied it), and connect an agent with `claude mcp add sagefs -- sagefs mcp` without racing the daemon's startup. A lot of the week was fixing places where SageFs said something that wasn't true, which is the boring part nobody sees and the part that decides whether you trust it.

### Edit a plain `let` value in a running app and it just lands
Before: change `let greeting = "hello"` to `"howdy"` and the app restarted, because SageFs had no way to know whether something had copied the old value, and "Patched" would have been a lie.
Now: SageFs reads the IL of every method in your project that touches a module value, works out which reads let the value escape into a field, closure or return, and watches those. If nothing kept a copy, the save is Patched and the running app serves "howdy" with the file's live state left alone. If something did keep a copy, you get a restart and the message names who kept it, down to the method and what it built around the value. A save that SageFs cannot prove reached the running process no longer gets called Patched either, and a file-watch overflow that resets your session now says so instead of doing it quietly.
Why it matters: you can tweak config-like values while the app keeps its state, and when it can't, you find out why instead of guessing.
Evidence: [Values table and how SageFs knows](https://github.com/WillEhrendreich/SageFs/blob/bba42706/docs/hot-reload.md#L171-L200), [the IL read classifier](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Middleware/ValueReads.fs#L273-L300), [no Patched without proof the copy the app calls was redirected](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/ReloadPlanning.fs#L1041-L1071)
Rough edges: the case people will hit first is that a page handler which renders the value hands it on, so once you've loaded that page, the next edit of that value is a restart (the docs say this in their own "falls short" list). Reflection reads after startup are watched in three modes you can switch live (`set_reflection_read_mode`, config, or the dashboard), and the hot-reload host runs with tiered compilation off by default so the watch can't be silently dropped, which costs warmup time.

### The daemon no longer walks into a symlink loop and eats your RAM
Before: starting the daemon from your home directory put it inside a recursive project scan with no cycle detection. A Wine prefix under Steam has a `z:` folder that points back at `/`, so the walk went around forever, 95% of a 6.2GB heap was path strings, and in two nights the daemon reached 51.7GB and 55GB on a 62GB machine. Five agents all rebuilding at once did the same thing by a different route, and nobody could say which one was misbehaving because nothing coordinated them.
Now: file discovery prunes excluded folders before it descends, refuses to follow directory symlinks, and stops at 64 levels or 50,000 entries while saying it truncated. Separately, the daemon reads the machine's available memory with hysteresis and acts on it: dead sessions are freed the moment they die, idle ones get stopped when memory is tight (never the one you are looking at), and at critical it refuses new sessions with a 503 and a reason. When the daemon's own memory first reads as broken it takes a gcdump so there is something to look at afterwards. Agents can ask for a lease before an expensive build, test run or app start (`acquire_full_build_lease` and friends) and get Granted, Wait with a retry time, or Refused.
Why it matters: leaving the daemon up on a laptop or a shared dev box stops being a gamble.
Evidence: [directory walk that cannot loop](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/SafeDirectoryWalk.fs#L30-L50), [shed-or-refuse policy and its guarantee about the session you are viewing](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/MemorySupervisor.fs#L1-L44), [the lease pool](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/ExpensiveWorkLease.fs#L1-L35)
Rough edges: the symlink walk explains the incident we took a process dump of, but a ten minute idle-daemon test I wrote could not reproduce the reported 2GB a minute, so I would not claim every runaway is closed. Machine memory is read from /proc/meminfo on Linux and approximated from the process's own view elsewhere, so the pressure numbers are weaker on Windows and macOS.

### /health says which signal broke, and `sagefs stop` can tell a wedged daemon from no daemon
Before: the daemon sat at 51.7GB with every session Ready and /health reporting healthy, and `sagefs stop` printed "No daemon running" while the old process kept the port, so the next start failed to bind and looked like start was broken.
Now: the daemon keeps a detector per signal (memory, /health latency, mailbox depth, eval latency) and /health carries the baseline, the current value and how long it has been off. A broken signal makes the daemon Unhealthy even when every session is fine. `sagefs status` reports a wedged daemon with its pid and `sagefs stop` kills it directly instead of waiting on an HTTP shutdown that will never answer. A daemon on a non-default port has to name an owner or a TTL, so a test daemon can't outlive whatever started it.
Why it matters: when something is wrong with SageFs you get a sentence about it instead of a green light and a dead machine.
Evidence: [per-signal watch](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/HealthWatch.fs#L18-L50), [EWMA plus CUSUM detector](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/HealthAnomaly.fs#L1-L40), [NotRunning, Running or Wedged](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/DaemonState.fs#L31-L55)
Rough edges: a plain "drifting" verdict does not flip health on its own, the machine memory pressure reading is what makes the daemon unhealthy in the memory case.

### Starting, stopping and cancelling no longer hang forever
Before: pointing a session at the F# compiler checkout left it in "Starting" for 20+ minutes with nothing to look at, `stop_session` on it hung for the full 300 second client timeout, and `cancel_eval` on a runaway loop left the session wedged so the next eval hung too (a second thread got started on the same live FSI session).
Now: warmup is judged by inactivity, not just elapsed time. Any progress resets a 30 second clock and a 10 minute ceiling applies regardless, so a big repo can take minutes but a silent one gets caught in 30 seconds. Stop has a hard ceiling. After a cancel the session sits in a Cancelling state and a new eval is rejected straight away with a message that names `hard_reset_fsi_session`. The blocking readers that were pinning thread pool threads for every session's lifetime now run on their own threads, which is what had been starving the daemon's own timers.
Why it matters: when a thing is stuck you hear about it in seconds, and the message tells you the next move.
Evidence: [warmup inactivity and ceiling](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/WarmupSupervision.fs#L28-L60), [the 30s and 10 minute defaults](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Timeouts.fs#L47-L57), [Cancelling blocks resubmit but keeps hard reset reachable](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/AppState.fs#L172-L177)
Rough edges: a cancelled eval still can't be un-cancelled, you recover with a hard reset.

### "Ready" means a project actually loaded, and a faulted session says why
Before: a session pointed at a directory with no projects came back Ready with `loadedProjects: []`, and a warming session could report `state: Ready` right next to `lifecycle: Starting`. An agent that gates on Ready walked into a session with nothing loaded and every eval failed with "not defined". A faulted session just said "run reset", with the real reason only in `/api/sessions`.
Now: if you named a project (or there was something to auto-discover) and none of it resolved, the session faults and the message names exactly what you asked for and what to check. A named project can't be reported Ready by a live status poll until the daemon's own check has run, state, lifecycle and loaded projects all come from one reconciled status so they cannot disagree, a Faulted or Stopped session can't be resurrected by a stale worker reply, and every tool and `get_fsi_status` carries the fault reason. A session that is busy evaluating stops reading as Stale (it is now called Idle, and only a Ready session nobody has touched goes idle).
Why it matters: you and your agent can trust the word Ready.
Evidence: [the earned-Ready gate](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/ProjectResolution.fs#L18-L76), [the daemon faults on RequestedButUnresolved](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/SessionManager.fs#L1384-L1392), [one reconciled status for state and lifecycle](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/Mcp.fs#L1440-L1450)
Rough edges: the VS Code extension's own readiness check was moved to the daemon's health verdict (`cf4218e0`), but I only read the parse, I did not click through it.

### Connecting an agent works the first time, and a restart doesn't strand it
Before: an HTTP MCP client that started before the daemon cached the failure and never retried, so you had no SageFs tools and no hint why. A client that outlived a daemon restart was permanently bricked, with an error telling it to call a tool it could not reach. A `switch_session` could be silently undone by an unrelated status poll during warmup.
Now: `claude mcp add sagefs -- sagefs mcp` starts a small stdio bridge that makes sure the daemon is up, waits for it, and only then shows your client its tool list. A stale session id re-binds to the one live session in that working directory, and refuses to guess if there are several. A deliberate `switch_session` survives warmup. The reset tools are callable from a session that never finished warming up (it used to be a catch-22). On connect, the agent is told the REPL loop, and there is a `back_to_the_repl` prompt for pulling a drifting agent back. A Claude Code hook can deny `dotnet build` while a Ready session covers that directory, and says BUSY rather than broken when the daemon is under load.
Why it matters: the first minute with an agent stops being a debugging session of the connection.
Evidence: [the stdio bridge decision core](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/McpBridge.fs#L186-L260), [stale id recovery that refuses to guess](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/StaleSessionRecovery.fs#L66-L90), [the repl guard decision](https://github.com/WillEhrendreich/SageFs/blob/bba42706/tools/agent-hooks/ReplGuard.fs#L274-L290)
Rough edges: in a git worktree, tools resolve to Gone with a create hint instead of falling back to the main checkout's session, which is correct but surprises people. The Claude Code hook is a Claude Code thing and nothing for other agents yet.

### What the agent reads back is true
Before: after a run the agent saw "12605 test result(s) received (Fresh)" right next to "0 passed, 0 failed", which a small model reads as 12,605 passing tests, when the payload was pure discovery. Server instructions and replies told agents to call tools that no longer exist. A printed `ProjectOptions` came back as one 90,000 character result. ANSI escape codes from a colored test logger landed in the text an agent tries to parse. Three detected tests reported `Total=3 Passed=0 Failed=0` which looks like nothing happened.
Now: the line says discovered, passed, failed, not run, stale, running, and never prints the old shape. Retired tool names are a DU and a contract test checks that no agent-facing string mentions one against the real tool catalog. Eval results are capped at 4,000 characters with a note saying how much was cut and a drill-in that works (`it` still holds the whole value in the session). ANSI is stripped from eval and script-load output. Every test status now falls into a summary bucket, and the unknown cases take the conservative answer, so a test with no result is never counted as passing. When live testing can't find the worker proxy the warning names which piece is missing.
Why it matters: an agent that reads a green line can't be fooled by a run that never ran.
Evidence: [test accounting line](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpPushNotifications.fs#L120-L140), [retired tools as a DU](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Affordances.fs#L366-L380), [the 4,000 char bound](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/EvalResultSummary.fs#L20-L40)
Rough edges: at this point SageFs had no tool that ran your test suite for you. It ran tests through the live-testing engine and you read them with `list_tests`. That changed on September 30, and the last stretch below has the `run_tests` tool.

### Big and unusual repos load: the F# compiler, Arcade layouts, pinned SDKs
Before: three onboarding trials on dotnet/fsharp all hit a wall. Arcade repos carry their own SDK and point global.json at it, SageFs built its FSI host with a different one, and died with "compatible .NET SDK was not found". Projects that reference a multi-targeted library loaded the first TFM and said "isn't built yet" about a project that was built. A preview SDK on the machine poisoned MSBuild loading for the whole daemon. The file watcher had hit its 50,000 directory cap silently, because the compiler repo has 76,596 directories and 74,582 of them are scratch under `artifacts/`, and then it used one inotify instance per directory and fell over at 975.
Now: the host builds with the SDK the project asked for, the daemon's own MSBuild variables are scrubbed from every child process (one list, one function), multi-targeted references are reloaded at the TFM the consumer actually builds, a newer-major SDK is never loaded in-process, `artifacts/bin/<Project>` is found when there is no `bin/`, and `sagefs check` stops reporting the oldest SDK as missing. The watcher is one recursive watch per root, with excluded folders filtered at event time, and when it fails it reports into /health instead of looking healthy. The missing-DLL error lists every path it checked with its TFM, so you can tell not built from looked in the wrong place.
Why it matters: SageFs works on the big, odd repos where a live REPL would help most.
Evidence: [skip a newer-major SDK in-process](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/ProjectLoading.fs#L571-L601), [one recursive watch, excluded subtrees filtered at event time](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/FileWatcher.fs#L400-L460), [the one list of poisoned variables](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/ProcessEnvironment.fs#L1-L30)
Rough edges: the watcher design flipped mid-week after I measured the compiled binary instead of `dotnet fsi` (the first fix was wrong, the commit says so), and a daemon started from a scratch directory like /tmp still inherits it as a permanent watch root.

### Your `use` bindings are no longer silently turned into `let`
Before: SageFs rewrote every indented `use` to `let` before handing code to FSI, on the way in for evals and for your own init.fsx. The stated reason was that FSI can't take `use` in expression context. That is false on the shipping toolchain, and the cost was real: streams left open, handles held, transactions never rolled back, in your code, changed by us. Separately, a project's own compiled `use` inside `task { }` died with MissingMethodException because the host's FSharp.Core won over the project's (issue 141).
Now: the rewrite is gone and `use` behaves as written. The project's FSharp.Core now resolves for the project's code, repointing only the type references whose signatures differ instead of renaming the whole assembly. The `SAGEFS_ISOLATED_FSI` opt-out is deleted so one stray env var can't drop you back into the shared-FSharp.Core mode.
Why it matters: SageFs's REPL now runs the code you wrote, not an edited copy of it.
Evidence: [commit removing the use to let rewrite](https://github.com/WillEhrendreich/SageFs/commit/4ab42550), [the in-place FSharp.Core fix](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/IsolatedFsiSession.fs#L450-L470), [where it runs after shadow-copy](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/ActorCreation.fs#L140-L150)
Rough edges: the first FSharp.Core fix (rename the whole assembly) broke live-testing discovery, the second one is narrower, and a Release build of your project sidesteps the original failure anyway.

### The dashboard stops yanking you around
Before: scroll up to read something and the next eval threw you back to the bottom. The sidebar showed hot reload, live testing, cohort and friction panels to everybody, always. Picking a workflow in the dropdown did nothing (the server saw an empty target). A busy session mid-eval read as Stale after ten minutes.
Now: output follows new evals while you sit at the bottom and holds still once you scroll up, with a "3 new evals" pill you can click or hit Enter on. Panels only appear when they apply: hot reload when the viewed session is in the Hot Reload workflow, live testing only if it's on, cohort only while members are present. Hidden panels carry their reason. The workflow dropdown sends what you picked, and the sidebar's "evals: N" finally shows a number. Enter on a focused button now clicks it.
Why it matters: the dashboard stops showing you controls that do nothing for the session you are in.
Evidence: [panel visibility, one decision per panel](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/DashboardTypes.fs#L1326-L1362), [chat-style output panel and the unseen-eval pill](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/DashboardFragments.fs#L825-L860), [activity touches so busy is never idle](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/WorkerProtocol.fs#L505-L520)
Rough edges: the friction panel is hidden unless you open `/dashboard?panels=friction`, because there is no real endpoint to send reports to yet.

### SageFs tells you when you're running a stale daemon
Before: a daemon started before your code changed kept serving the assemblies it started with, and nothing said so. An agent lost a whole session reading that as "SageFs is broken" and routing around it with dotnet, when restarting one process was the fix.
Now: for a tool install, the daemon checks NuGet (one request, 3 second timeout, cached on disk, re-checked every 6 hours) and says so in `get_fsi_status`, /health, `sagefs status` and a startup log line, but only when it is sure it is behind. A local build never claims to be stale, and a failed or skipped check never reads as "you're current". Related: `get_fsi_status` now reports the SageFs.Core version loaded in the worker, not the daemon's, since a rebuild only respawns the worker.
Why it matters: "restart the daemon" gets said before anyone burns an hour.
Evidence: [the pure outcome type](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/UpdateCheck.fs#L53-L57), [the NuGet fetch and cache](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/UpdateCheckService.fs#L21-L23), [how /health reports it](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpServer.fs#L2450-L2470)
Rough edges: it only knows about the NuGet tool install, so a source build (which is how I run it) gets silence, not a nudge.

### Hot reload is learning when a restart can skip the build (opt-in, early)
Before: a type change under a scoped restart still paid a full `dotnet build` every time, because SageFs could not tell whether anything alive still held an instance laid out by the old type, and reflection cannot answer that.
Now: an app can keep state in a registered holder and declare which unit is a restart boundary, and the restart decides from evidence whether a build is needed. If SageFs cannot establish that nothing alive holds the old shape, it pays the build, so the safe answer is the default. The whole decision chain is reachable from a save, a user's build gets SageFs's reference injected so nothing needs to go in the .fsproj, and the ConsoleTicker demo holds its counter this way.
Why it matters: later, when you edit a record your app holds, the respawn doesn't have to wait on a build or drop your state.
Evidence: [the three restart outcomes, including carry the value and skip the build](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/RestartCost.fs#L36-L55), [the app-facing boundary registry](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/RestartBoundaries.fs#L140-L180), [build injection](https://github.com/WillEhrendreich/SageFs/commit/07848ce3)
Rough edges: this is opt-in and aimed at Run App projects, a scoped restart is not yet cheaper than a whole one on its own (width and cost are different questions), and the piece that builds the new value for a changed type did not land until 09-27, after this window.

## Hot reload that keeps your state, live tests that don't lie, and sessions that run on their own .NET (2026-09-15 to 2026-09-21, 387 commits, v0.6.517 to v0.6.782)

By the end of this week you could save a file in a running Falco app and have the change land in the process that is already serving requests, with your counters and caches still holding their values, and with SageFs telling you plainly when it could not do that. You could edit a test project and have the affected tests rerun against code you had not saved yet, without a body-only edit slipping through as green. Every session now runs in its own host process on whatever .NET your project needs, the tool installs on a .NET 10 or a .NET 11 SDK, and when something goes wrong the message points at your line of code instead of a wall of framework frames. You could also pick the mode a session runs in (REPL, live testing, hot reload) from MCP, VS Code or a dropdown on the dashboard.

### Save a file and the running app changes, or SageFs says why it didn't
Before: a save that only re-pointed some helper functions, and none of the handlers you edited, was logged as "Hot reloaded" and the browser refreshed into the old code. For an app started from an init script, a save could also patch a copy of the function nobody was calling: it reported success on .NET 11 and restarted the app for no reason on .NET 10.
Now: SageFs works out which copy of a function your app is really holding and patches that one, and every save ends with one stated outcome about the running process, with the reason and the fix when it needs a restart. A handler written as a lambda bound to a name (`let handler : HttpHandler = fun ctx -> ...`) and an edit to a member body inside a type now reload instead of asking for a restart. The shape matrix test that pins each F# binding shape runs against a real host.
Why it matters: when you press save and reload the page, you are looking at what you typed, or you are told why you are not.
Evidence: [the code-shape table with the test that pins each row](https://github.com/WillEhrendreich/SageFs/blob/bba42706/docs/hot-reload.md#L97-L112), [the pairing against the copy the app holds](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Middleware/HotReloadCore.fs#L926-L952), [the one place an outcome becomes a browser event](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/ReloadBroadcast.fs#L1-L14).
Rough edges: a function that touches a private function or type in its file, a changed signature, and a handler built once at startup (`let h : HttpHandler = Response.ofHtml ...`) still mean a restart, and the doc says so.

### Your counters and caches survive a save
Before: editing a function in a file with a `let mutable` could reset the live value to its initializer, and editing the initializer was a restart (or, when SageFs was not the one running your app, a whole-file re-eval that quietly reset the state).
Now: a public or private `let mutable` keeps its live value when you edit a function that uses it. Edit the initializer from 10 to 25 while the app holds 13, and the app keeps 13 and the save says so, something like `kept 'App.State.tuned' = 13 (your new initializer 25 applies when you reset it)`. The dashboard's Hot Reload panel lists every kept value with a Reset button, and the `reset_hot_reload_state` MCP tool does the same. Changing the type (`= 1` to `= "one"`) is checked against the running app, not just your annotation, and that one is a restart.
Why it matters: the minutes you spend rebuilding app state after every tweak go away, and SageFs never keeps something without telling you.
Evidence: [the state table, with the real-app test for each row](https://github.com/WillEhrendreich/SageFs/blob/bba42706/docs/hot-reload.md#L152-L170), [the planner choosing "patch and keep state" over a restart](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/ReloadPlanning.fs#L960-L972), [the kept-state notice and Reset button on the dashboard](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/DashboardFragments.fs#L2488-L2510).
Rough edges: the Reset button only re-runs the initializer, so an initializer that uses something private in its file gets a restart instead of a kept value.

### Live tests rerun against unsaved code, and a body-only edit can't go green by accident
Before: as-you-type live testing selected tests by which symbol names changed. Rewrite `a + b` to `a - b` and no name changes, so zero tests were selected and the run reported green on a real regression. Flake history was also thrown away on every daemon restart, so no test could be demoted until its window refilled.
Now: an edited buffer is evaluated into the session and only the affected tests run against that fresh code, on keystrokes and on save. When a save changes no names, selection falls back to every test that reaches a symbol the file declares. Flaky tests get quarantined out of the next selection with a line in the session output saying so, and the flake history is written to the test cache so it survives a restart.
Why it matters: red goes green when you fix the code, and a quiet green means something ran.
Evidence: [the buffer-eval effect and the file symbol delta](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/LiveTestingTypes.fs#L3319-L3386), [quarantined tests excluded from the next run, and said so](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/SageFsApp.fs#L1566-L1574), [the flake section in the test cache](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/TestCachePersistence.fs#L118-L126).
Rough edges: if the dependency graph has not yet seen the test file that covers a symbol, the narrow still finds nothing, and the code names that limit itself. The fallback is the whole discovered suite on a cohort landing, not on a keystroke.

### Your project's packages can't collide with SageFs's, and each session runs on the .NET it needs
Before: the FSI session lived in a process that also held SageFs's own assemblies, so a project pinning a different FSharp.Core or System.Text.Json could get mangled, and a net11 project could not warm up at all because the host ran on net10.
Now: every session runs its FSI in a separate host process that links no SageFs assembly, started on the runtime the project's own build asks for. The worker no longer loads your assemblies at all, and the tool itself ships a net10 and a net11 payload, so `dotnet tool install` works on either SDK.
Why it matters: whatever versions your project pins are the versions your code runs against, on the .NET you chose.
Evidence: [session kinds, and why there is no opt-out](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/SessionKinds.fs#L5-L11), [picking the host's runtime from the project's runtimeconfig](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/RuntimeSelection.fs#L1-L25), [the tool multi-targeting net10 and net11](https://github.com/WillEhrendreich/SageFs/blob/bba42706/Directory.Build.props#L11-L22).
Rough edges: an unbuilt project has no runtimeconfig to read, so SageFs needs the project built before the session starts, and .NET Framework projects are refused (see the project shapes entry).

### When something breaks, the message points at your code and says what to do
Before: a failed eval printed the whole exception text with the one useful line buried under FSharp.Core and FSI frames. A not-yet-built project told you to leave the tool and run `dotnet build`. A session could read Ready and green after loading nothing.
Now: a runtime error leads with the exception type, the message and the first frame in your own `.fs` file, and the dashboard folds the framework frames and promotes the assertion line. A build that fails with a cluster of "X is not defined" errors for names that live in a later file gets a hint naming the file to move. A session that loaded nothing it was supposed to load reads Degraded, with the real warmup reason, in the API, in `get_fsi_status`, and on the dashboard card. A not-yet-built project points at the in-tool rebuild.
Why it matters: the first screen of an error says what to fix, and Ready stops meaning only "a process is alive".
Evidence: [runtime errors led by your own source frame](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/ErrorMessages.fs#L136-L167), [the compile-order hint on a failed build](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/CompileOrderInsight.fs#L165-L177), [the session health verdict](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/SessionHealth.fs#L20-L32).
Rough edges: the main Degraded trigger is a project that was expected while warmup loaded zero assemblies and opened zero namespaces, so a partial failure can still read Healthy (the code says why "any failed open" was too noisy to use).

### Pick the mode a session runs in: REPL, Live Testing or Hot Reload
Before: there were two workflows, hot reload was called "Live", an agent could not start a hot-reload session at all through MCP, and the dashboard showed the workflow as a read-only badge.
Now: a session runs in exactly one of REPL, Live Testing or Hot Reload, and there is no way to ask for hot reload on top of a full REPL because that combination does not exist as a value. A Live Testing session turns the test watcher on by itself the moment it is ready. You choose the mode when you create a session over MCP or HTTP, and you switch a running session from MCP, from VS Code's Switch Workflow command, or from a dropdown on the dashboard. A typo in the workflow name is rejected instead of quietly giving you a REPL.
Why it matters: you pick the loop you want for the work in front of you (explore, TDD, or a web app) and the session is set up for it.
Evidence: [the closed set of workflows](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/WorkflowTypes.fs#L355-L366), [what each mode does and how to switch](https://github.com/WillEhrendreich/SageFs/blob/bba42706/Readme.md#L213-L244), [the MCP tool telling you hot reload needs Live mode](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpTools.fs#L1133-L1139).
Rough edges: switching restarts the session, so REPL definitions and cell state are gone, and `live` still means Hot Reload on the command line for historical reasons. The dashboard dropdown shipped on 09-20 but did not send your pick until a fix on 09-22 (commit 2e4c20c2), so inside this window it looked right and did nothing.

### Oxpecker, plain ASP.NET and Raylib projects load, and an unsupported project is refused with a true reason
Before: Oxpecker and Minimal API projects were not recognised as web apps. A Raylib-cs project could kill the whole worker with a native crash on a background thread. A .NET Framework project got told it "has not been built", which was false.
Now: Oxpecker and plain ASP.NET Core projects are detected, including ones that reach ASP.NET through the Web SDK instead of a package reference. The worker resolves a hosted project's native libraries from the project's own output, so Raylib no longer takes the worker down, and desktop UI frameworks (Avalonia, MAUI, WinUI, Uno) are classified as native GUI so they skip the web patch. A net48 project is refused up front, naming the project, its target framework and why.
Why it matters: if SageFs can host your project it does, and if it can't, it says so in one sentence instead of failing at warmup.
Evidence: [the framework support table](https://github.com/WillEhrendreich/SageFs/blob/bba42706/docs/ecosystem-compatibility.md#L44-L47), [native library resolution for hosted projects](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/NativeResolution.fs#L9-L20), [the hostability verdict that refuses .NET Framework](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/ProjectCompatibility.fs#L78-L90).
Rough edges: .NET Framework is not supported and needs a second host that has not been built (the doc links issue #135).

### The dashboard stops lying about the daemon, and a stuck eval has a Cancel button
Before: if the daemon died mid-stream the dashboard sat there looking fine. A runaway eval left you no option except killing the daemon and losing every session. A console or game app started with `run_app` had no visible output, and once its output did flow, a continuous ticker grew daemon memory into the multi-GB range.
Now: the server sends a heartbeat and the browser compares it against its own clock, so a dead daemon shows the disconnect banner and clears it when the daemon comes back. A Cancel button appears while an eval is in flight. A `run_app` app's stdout shows in the session output, batched at most every 150 ms, and in the commit's live check daemon memory stayed around 240 MB over 40 seconds of a one-line-a-second ticker.
Why it matters: you can trust what the page says about the daemon, and a mistaken `while true do ()` no longer costs you the whole daemon.

## Run your app, trust what it tells you (2026-09-01 to 2026-09-14, 438 commits, v0.6.339 to v0.6.517)

At the start of this stretch the Run App button was a stub, live testing showed "Discovering tests..." whether it was discovering or not, and any web page open in your browser could in principle talk to the daemon. By the end you can start your project's real app from a session and watch saves either patch it in place or restart it at the same address. Live testing says what it is actually doing, a bad build no longer takes your session down with it, and the daemon refuses requests from pages that are not its own. Agents also got a way to share one repo: claims, a landing queue, and a dashboard panel that shows who holds what.

### Run your project's app from a session, and a save either patches it live or restarts it where it was
Before: Run App was a fake. It guessed an entry-point file and never launched anything you could open, and the dashboard passed an empty project name.
Now: the session runs the real entry point of the project it loaded, from the dashboard card (status line, the real URL, an open-in-browser link, Stop) or from the run_app and stop_app agent tools. When you save, a planner reads your file and decides: a changed function body is patched into the running app, while a changed type, value, startup code, entry point or function signature stops the run, rebuilds, and relaunches at the same address so the browser tab you had open still works.
Why it matters: you edit, save, and refresh the tab you already had, and when SageFs cannot patch a change it tells you why and does the restart instead of quietly serving old code.
Evidence: [runApp](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/AppRunOrchestration.fs#L239-L260), [the plan a save produces: patch, patch keeping state, or restart with reasons](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/ReloadPlanning.fs#L136-L143), [the detour planner that stopped two copies of a function from jumping to each other](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Middleware/HotReloadCore.fs#L308-L331)
Rough edges: a console app that just keeps running has no server to stop in place, so Stop tells you to hard-reset the session instead.

### Live testing says what it is doing, in the same words everywhere
Before: with zero tests the panel said "Discovering tests..." forever, twelve tests that had never run read "0/12", and a failed discovery or a compile error looked the same as waiting. A save from vim or a JetBrains safe write (write a temp file, rename it over the source) was never noticed at all.
Now: each session has one live-testing state: off, looking for tests, discovery failed (with the reason), no tests found (with the framework it detected), waiting on a file to compile (file name and error count, showing the last good results), rebuilding, running, or settled. The dashboard and the VS Code status bar use the same wording, a failed rebuild shows the first compiler error instead of "Build failed (exit 1)", and a test the worker never reported on shows as stale instead of failed. Rename-style saves now trigger a run.
Why it matters: you can tell "it is compiling, give it a second" from "something is broken" without opening a log.
Evidence: [the states and their wording](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/LiveTestActivity.fs#L168-L188), [why a test has no result, and that it is not a failure](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/LiveTestingTypes.fs#L269-L288), [the file watcher now listening for renames](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/FileWatcher.fs#L443-L455)

### A failed rebuild no longer takes down the session you were working in
Before: a hard reset with rebuild stopped your worker first and then ran the build. Live testing takes that path on every save whose type-check fails, so one typo mid-edit left the session Faulted, and fixing the typo could not recover it because there was no worker left to check the fix. The rebuild also cleaned the outputs, so a failed compile deleted your DLL.
Now: the build runs first while the old worker keeps serving the last good build. If the build fails the session is left as it was and you get the compiler output as structured diagnostics (file, line, column, code). A session also loads the freshest of the Debug and Release outputs by write time, so a stale Debug build can no longer shadow the Release build you just made.
Why it matters: a typo costs you a red squiggle, not your REPL state.
Evidence: [the rebuild-completed handler: old worker keeps serving on a failed build](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/SessionManager.fs#L959-L990), [loading the freshest build across configs](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/ProjectLoading.fs#L336-L360), [build failures as data](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/SageFsError.fs#L15-L60)

### The daemon does what it says: stop stops, hung evals end, a wedged worker gets replaced
Before: `sagefs stop` printed "Daemon shutting down", exited 0, and the daemon kept serving. The HTTP calls to the worker had no timeout, so an eval stuck in an infinite loop hung whoever asked. One unhandled exception in the session manager killed its mailbox and orphaned every session. The session manifest could lose writes (the commit measured 20 concurrent purges leaving 19 of the 20 purged sessions on disk, three runs out of three), and a session whose directory you had deleted was retried and warned about on every start, forever.
Now: stop waits for the process to actually exit and kills it if it will not. Worker requests have a ceiling (ten minutes by default). The session manager catches a crashing handler, answers the caller with an error, and carries on with the last good state. A worker whose process is alive but stops answering is restarted after three missed health checks. The manifest has one writer, startup forgets sessions whose directory or projects are gone, and a restart now starts the replacement worker before retiring the old one. The idle standby worker that used to sit around per session is gone.
Why it matters: when SageFs says something happened, it happened, and a stuck eval or a crashed handler stops being a reason to restart the daemon.
Evidence: [the stop command waits for exit](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/Program.fs#L317-L348), [the supervised mailbox step](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/SessionManager.fs#L1532-L1560), [the hung-worker health probe](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/WorkerHealthProbe.fs#L18-L58)
Rough edges: the ten minute cap will cut a legitimately longer eval, and `SAGEFS_WORKER_HTTP_REQUEST_MINUTES` is how you move it.

### Other pages in your browser cannot make your daemon run F#
Before: the dashboard and MCP servers listened on localhost and checked nothing about who was calling. The commit that fixed it spells out the attack: a malicious page or a DNS rebinding trick could POST across origins, create sessions at arbitrary paths, and evaluate F# as you. A later pass found a page served from any other localhost port (a compromised npm dev server, say) counted as the same site, that `http://localhost.evil.com` passed a prefix check, and that a text/plain POST skipped the browser preflight.
Now: the Host has to be loopback, a browser Origin has to match one of the daemon's own origins exactly (parsed, never by prefix), and any POST with a body has to be labelled JSON. The worker's HTTP server got the same guard. The dashboard also stopped loading Datastar from a moving CDN branch and fonts from Google (both are served from the daemon now), HTML-encodes runtime strings (a bound string containing markup used to inject script into the live bindings view), and `SAGEFS_BIND_HOST` only accepts loopback values. curl, editors, MCP clients and the CLI send no browser headers and pass unchanged.
Why it matters: you can leave the daemon running and browse the web.
Evidence: [the origin decision](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/HttpOriginGuard.fs#L230-L258), [the gate wired into both servers](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpServer.fs#L686-L708), [loopback-only bind host](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/SageFsConfig.fs#L82-L119)
Rough edges: there is still no authentication, and a LAN bind is now refused outright with a message about port forwarding instead of being supported. A bearer token was considered and rejected in the commit because every client would need an auth flow.

### When something fails you get what, where, and what to try, as data
Before: `/exec` always answered success=true, so a compile error, a dead worker and a good eval looked the same. `check_fsharp_code` returned bare "[severity] message" lines with no position. Error categories were guessed from substrings across the whole message, stack frames included. `/health` sent a null error for a faulted session, so VS Code drew a bare error icon.
Now: `/exec` reports success=false with an error field when the eval failed (HTTP stays 200 because the request was processed) and a real error status when it never ran. `check_fsharp_code` gives line and column plus a suggested fix. MCP tool failures come back flagged as errors with a stable case name, message and suggested action, and `send_fsharp_code` returns structured diagnostics with spans next to its unchanged text. A faulted session shows its reason and a suggested action in `/health`, and no single tool result is bigger than 256 KiB.
Why it matters: an agent or an editor can branch on the result instead of reading prose, and you see where the problem is.
Evidence: [the /exec contract](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpServer.fs#L2043-L2062), [first-line, specificity-ordered classification, and by FS error number](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/ErrorMessages.fs#L16-L56), [send_fsharp_code's structured result](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpTools.fs#L676-L722)

### Agents get a smaller, truer tool surface
Before: eighteen feature tools (diagnose, impact_forecast, plan_ripple, export_notebook and friends) were written but never registered, so no agent could reach them. Every tool ran in every session state. `get_available_projects` answered with 161 KB and 1,620 lines because it walked into every agent worktree. `create_session` split the documented JSON-array form of `projects` on commas, so an agent that followed the docs loaded a bogus path and still got a Ready session. Now: the eighteen tools are registered (the commit counts 20 going to 38 at that time), every tool call is checked against the state of the session it targets and refused with a clear reason when that session cannot take it, the project list is capped at 40 with a "N more, narrow with working_directory" note, `create_session` accepts the array form, session-create paths must stay inside the working directory, and pure-MCP evals land in the event history. Agents can also read `cohort://status` and `sessions://list` as MCP resources and subscribe to updates instead of polling.
Why it matters: the agent sees what it can actually call right now and the answers it gets back are true.
Evidence: [the gate that classifies every tool](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Affordances.fs#L170-L180), [the project-list cap and the tolerant projects argument](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpAdapter.fs#L40-L90), [the two MCP resources](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpResources.fs#L46-L60)

### Several agents can work in one repo through claims and a landing queue
Before: two agents in the same repo had no way to know about each other. Worktrees were also routed wrongly, because a session lookup from inside a worktree walked past its `.git` file up to the main checkout.
Now: agents join a cohort, claim files or projects (with fencing tokens so a stale claim cannot win), and queue a landing. A landing is rebased in a real git worktree, verified, and fast-forwarded in, strictly one at a time. Verification runs only the tests whose coverage touches the diff (a test with no trustworthy coverage always counts as affected) and takes results from a content-addressed cache when the inputs are unchanged. A landing that could not be verified is marked inconclusive and does not jam the queue. The dashboard has a cohort panel, a worktree is its own routing boundary and shows its branch in `list_sessions`, and `sagefs play` replays a saved ledger file offline. A dogfood test drives two separate MCP connections through join, conflicting claims, a refused role, and real landings.
Why it matters: you can point two or three agents at one repo and see who holds what, instead of finding out in a merge conflict.
Evidence: [landing states and the blocker kinds, including inconclusive](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Cohort.fs#L253-L289), [narrowing verification to the diff](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/AffectedTests.fs#L1-L30), [the request_landing tool](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpTools.fs#L2425-L2446)
Rough edges: it is claims v1. A daemon holds one cohort, the first agent to join becomes conductor with no way to hand that over yet, and identity follows the MCP connection, so agents that share one connection count as one member.

### The dashboard stays fast, and the eval history stops getting slower as a session grows
Before: the dashboard re-rendered and re-sent the whole page on every timer tick even when nothing had changed, with a fixed 100 ms coalescing delay on pushes. At the history cap, every eval triggered a full rescan of the retained cells (the commit measured one such rebuild over 10,000 cells at about 100 seconds on the old build), and an idle session with 9,607 discovered tests kept the daemon's message loop busy with a 25 ms timer that had nothing to do.
Now: a tick whose snapshot has not changed skips the render and the send, the stream is compressed, and the fixed delay is gone. Per the commit, eval-to-pixel on a warmed worker settled at 2.7 to 14.4 ms, from a 100 ms+ floor. Recording an eval costs about the same at 100 cells as at 10,000 (0.011 ms against 0.060 ms in the Debug harness), the history lives in fixed-size chunks so the 10k-versus-1k scaling ratio dropped from about 5x to about 1.1x, and live bindings are pulled after the reply instead of being built before it. The test timer idles unless a debounce is pending, and coverage travels as a packed bitmap, roughly a fortieth of the old JSON size by the commit's estimate.
Why it matters: a long session keeps answering as fast as a fresh one, and the browser tab stays quiet when nothing moved.
Evidence: [skip the render on an unchanged tick](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/Dashboard.fs#L1340-L1352), [recording an eval at a flat cost](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/EvalStore.fs#L298-L312), [the eval-to-pixel latency trace](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/EvalLatencyTrace.fs#L37-L40)

Evidence: [choosing which session to show](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/Dashboard.fs#L533-L556), [the single-column layout at narrow widths](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/dashboard.css#L1444-L1475), [the coverage treemap](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/DashboardFragments.fs#L1444-L1452)

### A session that says Ready can actually see your project
Before: warmup would report success without checking that your project's assemblies had loaded into the session. You got a green Ready, typed something, and every `open` failed with "not defined".
Now: after warmup, SageFs compares the assemblies your projects should have produced against what the session really loaded. If none loaded, the session goes Faulted with a reason and FSI's own init errors attached. If only some loaded, the log names exactly which are missing. When the project loader returns zero projects inside the daemon's worker (it did this, even though FSI itself was fine), SageFs falls back to reading the .fsproj by hand so you still get your source files and namespaces, and warmup warnings like missing DLLs or zero namespaces show up in the dashboard's "Failed Opens" section.
Why it matters: the status light means something now, so you stop debugging a session that was never loaded in the first place.
Evidence: [the load classifier](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/WarmUp.fs#L125-L149), [where warmup faults on it](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/AppState.fs#L926-L959), [the manual .fsproj fallback](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/ProjectLoading.fs#L73-L80)
Rough edges: "some assemblies missing" is a log warning, not a fault, so a half-loaded session still reads Ready.

### Your project's package versions stop fighting SageFs's
Before: the worker process carried SageFs's own web dependencies (Falco, OpenTelemetry, Datastar). If your project used different versions, say a Falco 6 beta, FSI bound SageFs's copy first and your app failed to load with a 0x80131040 error.
Now: the F# Interactive session runs in its own small host process, `SageFs.Host`, which references only SageFs.Core and ASP.NET. Falco and OpenTelemetry live in the daemon and never enter the host. The host also checks its own folder at startup against a manifest of the files it was built with and refuses to start if anything extra is in there. Before that split, an interim fix moved aside any bundled DLL that your project's bin also had; the commit says it was verified live on a Falco 6 beta project (I didn't rerun that for this page), and that interim code is gone now that the host replaced it. A startup crash loop also gives up after 3 tries instead of 5, with a longer backoff, so a host that can't start fails fast.
Why it matters: a real web project with its own dependency pins is exactly what you point a REPL at, and it no longer loses to the tool's own copies.
Evidence: [host references only Core + ASP.NET](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Host/SageFs.Host.fsproj#L29-L30), [the fail-closed startup check](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Host/Program.fs#L35-L39), [the interim quarantine fix that the host replaced](https://github.com/WillEhrendreich/SageFs/commit/fe521357)
Rough edges: the host still carries FSharp.Compiler.Service, Fantomas, Cecil and Harmony through Core. A "swap in a version-matched variant" planner was written and tested in this stretch, but nothing calls it at this commit, so a project pinning a different Fantomas or FCS is not handled yet.

### Watch your bound values live, like a debugger watch window
Before: the bindings panel was FSI's printed `val x : T = v` text parsed back into rows, so a record or a list was one flat string.
Now: after every eval the worker walks the real runtime values and ships a snapshot to the dashboard, which renders an expandable tree. Records, lists, maps, unions, tuples, arrays and class properties expand, closure captures are shown and flagged as best-effort, and cycles and truncation are marked instead of hidden. Only the bindings panel updates, and only when the values structurally changed.
Why it matters: you can see what the session actually holds after each eval without typing `x;;` for everything.
Evidence: [the value walker](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/LiveValueTree.fs#L8-L16), [the change-only store](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/LiveBindingsAdaptive.fs#L28-L55), [the dashboard panel](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/DashboardFragments.fs#L3517-L3556)
Rough edges: the walk is capped (depth 6, 50 children, 200 top-level bindings), so a huge session shows a truncation marker rather than everything.

### Kill the daemon the hard way and nothing keeps running
Before: if the daemon died without a clean shutdown (Task Manager, `taskkill /F`, a crash, the OS going down), its worker processes sat waiting for a shutdown message that never came, and stayed around as orphans (issue #126).
Now: the daemon hands each worker its own PID, and the worker checks every 2 seconds that the daemon is still there. If it's gone, the worker shuts itself down. The check compares the daemon's start time as well as its PID, so a recycled PID can't keep a worker alive, and any lookup error counts as "gone".
Why it matters: you stop finding gigabytes of dead sessions in the process list after a crash.
Evidence: [the liveness check and loop](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/OwnerMonitor.fs#L73-L125), [the worker wiring](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Host/WorkerMain.fs#L1928-L1945)
Rough edges: it's a 2 second poll, because there's no portable event to wait on for a process that isn't your child.

### Stop a session and get it back, or purge it for good
Before: stopping a session gave no immediate feedback, and there was no clean way to throw away a corrupted session's saved state.
Now: Stop unloads the session and keeps its entry under "Resume Previous". Purge stops it and deletes its entry from the saved manifest, the "delete obj and bin" move for state that went bad. The dashboard swaps the session card to "Stopping session..." right away, clears the output if you were looking at it, then moves you to the next session, or to the session picker if none are left.
Why it matters: you can park a session you want back, and nuke one you don't, without waiting on the daemon to tell you what happened.
Evidence: [the teardown operations](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/SessionMode.fs#L47-L50), [stop and purge in the daemon](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/DaemonMode.fs#L600-L644), [the dashboard routes](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/Dashboard.fs#L3246-L3254)
Rough edges: this shipped as three tiers (stop, dispose, purge), but dispose later became the same call as stop because the per-session replay file went away, so today the dashboard has a Dispose button that does what Stop does ([original commit](https://github.com/WillEhrendreich/SageFs/commit/055571d2)).

### Agents get tool errors they can read and optional arguments that are optional
Before: an agent that left out an optional argument (say `block_start_line` on `send_fsharp_code`) crashed inside the MCP library, because the schema marked it required. Tool exceptions came back as raw stack-shaped text.
Now: every optional parameter across the registered tools has a default, so omitting it works. Any exception a tool throws is turned into a proper error result (marked as an error, with the missing parameter named if that's the cause). `enable_hot_reload` and `disable_hot_reload` are new tools that turn the hot reload patching on or off mid-session without losing your FSI state, and `disable` now really disables it instead of being cosmetic.Why it matters: if you drive SageFs from an agent, a bad call now tells the agent what to fix, and it stops falling over on its first malformed call.
Evidence: [optional parameters with defaults](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpTools.fs#L651-L662), [exceptions become error results](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpServer.fs#L376-L408), [the hot reload tool replies](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpTools.fs#L482-L490)
Rough edges: after `enable_hot_reload` you still have to cancel your running web app and re-evaluate it for the middleware to apply, and hot reload itself was marked "in progress" in the README on Aug 27 because changes weren't reaching running module-declared apps yet.

### A reset or crash can't leave a session lying about its state
Before: `hard_reset_fsi_session` with rebuild ran as fire-and-forget and never updated the status snapshot. If the rebuild failed the session stayed "Restarting" forever, and `get_fsi_status` and `list_sessions` could disagree about whether it was Ready.
Now: a reset moves the status to Starting, then to Ready or Faulted with the reason, whichever way it ends, including timeouts and transport failures. A session the daemon lost track of shows as "lost" in the sidebar instead of vanishing.
Why it matters: when something breaks you see Faulted with a reason and a way out, not an endless spinner.
Evidence: [reset moves status to Faulted or Ready](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/Mcp.fs#L1676-L1729), [the one status vocabulary, including Lost and Faulted-with-reason](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/SessionDisplay.fs#L12-L40), [the startup-crash circuit breaker](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/RestartPolicy.fs#L108-L130)
Rough edges: the soft reset gives up after 5 minutes, which is long to stare at a stuck session.

### One coverage badge per function in VS Code, not one line per test
Before: with live testing on, a function covered by 100 tests could get 100 inline decorations above it.
Now: the daemon projects coverage into one summary per function (for example "✓ 97 ✗ 3"), sends it to editors as a `coverage_view` event, and the VS Code extension shows a single CodeLens per function. The defaults never auto-collapse, because F# people write lots of tests per function, and a newer test run replaces older results so stale lenses go away.
Why it matters: you can see at a glance whether the function you're editing is covered and passing, and the editor stays readable.
Evidence: [the per-function coverage type and badge DU](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/TestAnnotations.fs#L506-L593), [the daemon emitting one event per function](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpServer.fs#L1620-L1630), [the VS Code CodeLens provider](https://github.com/WillEhrendreich/SageFs/blob/bba42706/sagefs-vscode/src/CoverageViewCodeLensProvider.fs#L14-L50)
Rough edges: the "collapse when over N tests" threshold exists in code but there is no editor setting wired to it yet, and I didn't check whether the Neovim plugin renders the new event.

### Dashboard tabs stay independent, and each project remembers its theme
Before: the daemon had one global "active session", so switching sessions in one place could change what another view showed, and the theme was one global choice.
Now: each browser tab has its own viewing session, and the dashboard layer can't read a global active session at all (the field was removed, so code that tried wouldn't compile). Theme choice is saved per project directory, with paths normalised so `C:\Foo`, `c:\foo\` and `C:/Foo` are one project, and there are 8 themes: One Dark, Kanagawa, Tokyo Night, Gruvbox, Catppuccin Mocha, Monokai, Dracula and Nordic. The layout was also redone as a flat tabline, sidebar and statusline, and the session cards were made single-column so they wrap instead of squeezing.
Why it matters: two tabs on two sessions don't trample each other, and your game project and your web project can look different.
Evidence: [the theme list](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/ThemePresets.fs#L99-L108), [the path canonicalisation behind per-project themes](https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/DashboardTypes.fs#L1480-L1495), [the commit that removed the global](https://github.com/WillEhrendreich/SageFs/commit/e3900e90)
Rough edges: the dashboard was reworked again right after this window, so what you see today differs from the redesign described in this stretch's changelog.

## The editor loop gets real: results on the line, tests as you type, and a daemon that doesn't need Docker (2026-03-01 to 2026-03-31, 635 commits, v0.5.406 to v0.6.241)

At the start of March, SageFs was a daemon you sent code to, and it wanted a Postgres container to remember anything. By the end you could hit Alt+Enter on a block in VS Code and see the value on the line, turn on live testing and watch the right tests rerun while you type, open a dashboard that shows your bindings, coverage and failures live, and restart the daemon without losing your sessions or starting Docker. Agents got a tool list that follows what the session can actually do, and a few tools that tell them what to verify next. There's also a pre-flight check and a first-run walkthrough now, so a new machine has somewhere to start.

### Alt+Enter an F# block in VS Code and the answer shows up on the line
Before: the extension was an early cut, and March opens with a run of reliability fixes (daemon lifecycle, SSE reconnects, crash detection) just to make it fit for the Marketplace.
Now: Alt+Enter evaluates the block around your cursor (blocks split on `;;` if the file uses them, on blank lines if not), the result lands inline, Shift+Enter evaluates and moves on, Ctrl+Up and Ctrl+Down jump between blocks, and Ctrl+Alt+Enter runs the lot. Binding values show up as ghost text, and a sessions tree and status bar menu let you switch, reset and stop sessions without leaving the editor. It publishes to the VS Code Marketplace and Open VSX from CI.
Why it matters: you stay in your .fs file and see values as you write, the way a notebook feels, without a terminal in the loop.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/sagefs-vscode/package.json#L285-L322 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/sagefs-vscode/src/Extension.fs#L3100-L3105 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/.github/workflows/publish.yml#L107-L127
Rough edges: the Visual Studio extension got the same treatment in March (sprints 2 to 12 in the log) and is deprecated now, so none of this is a claim about Visual Studio. See commit https://github.com/WillEhrendreich/SageFs/commit/5020205d

### You can evaluate a piece of a real project file, not just a scratch script
Before: a function copied out of `module Foo.Bar` has none of its opens or its module around it, so FSI has nothing to resolve it against.
Now: editors and agents send the file path, whether it's a whole file or a block, and the line the block starts on. SageFs parses the file's structure, wraps the block in its enclosing module with the file's opens, and maps compiler error line numbers back to your original file. The parse is cached per file and content hash, so repeated evals don't pay for it again.
Why it matters: you can poke at the middle of a real module with Alt+Enter and get errors that point at the lines you actually see.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpTools.fs#L652-L673 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Middleware/CompilationContext.fs#L519-L530 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/Mcp.fs#L915-L916

### Tests rerun as you type, and adding a comment doesn't throw away a run in progress
Before: test feedback was save-driven, and the test-cycle timer ticked every 200ms, so even the fast path got rounded up to the next tick.
Now: the editor streams your unsaved buffer to the daemon, the test cycle ticks every 25ms while a debounce is pending (the file watcher debounce went from 200ms to 75ms in the same commit), and a keystroke that only changes whitespace or comments is recognised as trivia, so it doesn't kick off a type-check and doesn't mark in-flight results stale. In a compiled project a keystroke runs the affected tests and a save triggers a rebuild first. Each session gets its own file watcher, so a background session reacts to its own files.
Why it matters: the red or green on your test changes while you're still typing the fix, and typing a comment doesn't make it flicker.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Timeouts.fs#L165-L182 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/LiveTestingTypes.fs#L94-L182 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/LiveTestingTypes.fs#L3595-L3618
Rough edges: the docs still call live testing "functional but still being stabilized" with Expecto the best covered, and the compiled-project path has been reworked since March (an unsaved buffer is now evaluated into the session instead of waiting on a rebuild), so the March commits describe where it started and not where it is.

### A failing test tells you which line, what changed, and which counterexample
Before: a red test told you it was red.
Now: SageFs pulls the first non-framework line out of the stack trace (skipping Expecto, FSharp.Core, System and Microsoft frames) so editors can jump to it. When a test goes from passing to failing it records a narrative: how long since it last passed, which symbols and files changed in between, and for an FsCheck property the shrunk counterexample. Failing tests run first, then tests that have never reported, then the ones that passed. Next and previous failing test are keybindings in VS Code, and an agent can ask for the same story with `explain_test_failure`.
Why it matters: when something goes red you start from "this changed, here's the line" and not from a diff of your last hour.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/Mcp.fs#L2390-L2420 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/LiveTestingTypes.fs#L2618-L2630 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpTools.fs#L1798-L1823
Rough edges: the "what changed" list is a correlation, not a proof, and the tool description says so itself.

### Live testing knows what kind of test each one is, and treats it accordingly
Before: a Theory with five InlineData rows counted as one test, and a slow integration test would be as eager to run on every keystroke as a pure one.
Now: xUnit (v2 and v3), NUnit, MSTest and TUnit are found by their attributes, Expecto is found by reflection with no compile-time dependency on it, and each InlineData row is its own test case (issues #38 and #39). Tests are sorted into categories, and the default policy runs unit and property tests on every change, architecture tests on save only, and integration, browser and benchmark tests on demand. A test whose source touches System.IO, HttpClient and similar is classed as integration without you tagging it. An FsCheck counterexample is reported as a real bug, never as "flaky", and environmental flakiness is demoted in the run order.
Why it matters: the fast loop stays fast because the slow tests wait for you to ask, and a property test that finds a bug doesn't get a flaky label.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/LiveTestingExecutors.fs#L289-L325 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/LiveTestingTypes.fs#L183-L211 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/LiveTestingTypes.fs#L1162-L1175
Rough edges: the docs say Expecto has the best coverage, which is another way of saying the attribute-based frameworks have had less mileage.

### Restart the daemon and your sessions come back, with no Postgres and no Docker
Before: session history went through Marten and a Postgres container SageFs started via Docker, and if neither was available the daemon exited with an error.
Now: sessions are written to one binary file (`daemon.sagefm`), checksummed over the whole file, written atomically through a temp file, with the previous copy kept as a `.bak` that load falls back to if the primary is corrupt. Your last test results are cached in a second binary file the same way. Marten and Postgres are gone from the code.
Why it matters: install the tool and run it, and a restart doesn't cost you your session list.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/ManifestPersistence.fs#L296-L345 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/DaemonPersistence.fs#L25-L48 , https://github.com/WillEhrendreich/SageFs/commit/5677d0e2
Rough edges: Postgres was made mandatory on March 2 (https://github.com/WillEhrendreich/SageFs/commit/2d416045) and removed on March 4, so for two days the tool was strictly worse than the day before it.

### The dashboard shows what's in your session: tests, coverage, bindings, failures
Before: tests were a sidebar list, and "what is bound right now" was something you remembered or went and asked.
Now: each session row carries test badges and a treemap coloured by pass, fail, running and uncovered, with a coverage drill-down. A bindings panel lists active bindings with their types and values and keeps shadowed ones in their own collapsed section. There's a daemon health panel (version, memory, uptime, per-session state), a failure narratives panel, an FSI diagnostics panel and an eval filmstrip. Most of those start collapsed, with a minimal mode that hides most panels until you expand, and clicking a session row highlights it before the server has answered.
Why it matters: you can look at one page and see whether your session is healthy and what your tests are doing, instead of asking an agent or grepping output.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/DashboardFragments.fs#L1444-L1461 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/DashboardFragments.fs#L3449-L3470 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/DashboardFragments.fs#L580-L590
Rough edges: because most panels start collapsed, a first look shows less than this paragraph implies.

### The browser reloads when you save, and shows you the compile error instead of a stale page
Before: a hot-reload save that failed to compile could leave the browser stuck on "recompiling".
Now: with the hot reload workflow on, saving a web app's .fs file puts a "compiling" pill on the page with elapsed time, then reloads and keeps your scroll position. A compile failure shows a red panel with the diagnostics, a few lines of source around the error, and a link that opens your editor at that file and line (VS Code by default, Cursor or Rider if `SAGEFS_EDITOR` or `EDITOR` says so). A loop guard stops runaway reloads, and it works behind a Content-Security-Policy by adding a nonce. Hot reload is its own workflow because it blocks redefining types in the REPL, and the workflow type has no case that combines the two.
Why it matters: you save, you see either the new page or the exact line that broke it, and you never have to look at a terminal to find out which.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Host/Resources/devreload.js#L36-L58 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Host/DevReloadMiddleware.fs#L20-L36 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/WorkflowTypes.fs#L352-L367
Rough edges: an app started with `run_app` restarts on save instead of being patched in place (docs/hot-reload.md has the table), and that restart resets the app's state.

### Agents are only offered the tools that make sense for the session's state
Before: an agent could call anything at any time and get a confusing failure back, and warmup messages invited sleep-polling loops and duplicate sessions.
Now: every tool call is checked against a table. While a session is warming up an agent sees status, session management and lease tools, and once it's Ready it also gets eval, tests, diagnose and the analysis tools. A tool nobody declared is refused, not allowed. A TypeLoadException tells the agent to remove the duplicate `#r` before it considers a reset, and warmup tells it to read recent events instead of looping on sleep.
Why it matters: an agent that can't call the wrong thing wastes fewer turns on a session that isn't ready yet.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Affordances.fs#L41-L110 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Affordances.fs#L163-L186 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/ErrorMessages.fs#L62-L70

### An agent can ask what to verify next, and the answer is allowed to be "I can't tell you it's green"
Before: an agent told you the change worked because the eval returned.
Now: `targeted_verify` plans the safest verification step for one changed behaviour, and refuses to claim green when the session's trust is ambiguous or the loaded code is stale. `diagnose` rolls six analyses (failure narratives, cell dependencies, staleness, ripple plan, next-cell suggestions, timing) into one report with a short summary. `suggest_next_action` ranks what to do next, failures first, then coverage blind spots, performance, stale cells and tests. `plan_ripple` and `preview_what_if` show which cells a change would touch without running anything.
Why it matters: an agent that says "this might be stale" is more use to you than one that says "done".

Rough edges: `run_tests` was removed from MCP on March 28 (https://github.com/WillEhrendreich/SageFs/commit/1961300a) and came back on September 30, so any March description of what an agent could do about tests is out of date.

### Two agents in one session can see each other
Before: a second agent evaluating in the same session had no idea the first one was there.
Now: SageFs tracks which agents are active in a session, what they said they were doing (the `intent` argument), and which files they recently evaluated from. When you eval from a file another agent recently touched, the result carries a note naming that agent and the files. The dashboard shows agent badges on session rows and tints a contested or unhealthy session.
Why it matters: you find out about an overlap from the tool that's about to cause it, not from a merge conflict.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/SessionOperations.fs#L146-L160 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/SessionOperations.fs#L222-L254 , https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/Mcp.fs#L1150-L1158

### A first run has somewhere to start: a pre-flight check, a walkthrough, and a pile of koans
Before: first-run problems like a missing SDK or an occupied port showed up as a daemon that wouldn't start.

## The first week and a half: from a REPL daemon to a daemon that runs your tests and talks to your editor (2026-02-20 to 2026-02-28, 403 commits, v0.5.18 to v0.5.383)

At the start of this stretch you had a daemon holding an F# Interactive session, a dashboard, and an MCP server, mostly driven from a terminal UI. By the end you could hit Alt+Enter in VS Code and get the result inline, edit a function and watch only the tests that reach it re-run, see coverage bars in the gutter, let an agent ask SageFs to run the tests and get a real verdict back, and save a file and have the browser reload without you touching it. You also no longer needed Docker running just to start the thing.

### Edit a function and only the tests that reach it re-run
Before: you ran the whole suite, or you picked tests by hand, and a build sat in the middle of every loop.
Now: SageFs finds your tests (even in a file that doesn't compile yet, because it reads the source with tree-sitter), builds a map of which tests reach which functions, and when you edit, it re-runs just those through the warm F# session. No MSBuild rebuild in the loop. It started out with a nasty bug where a single eval could trigger all 3,464 tests of the project, and that got fixed the same day it showed up.
Why it matters: you stay in the edit-and-see loop instead of waiting on a build and a full test run.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/TestTreeSitter.fs#L1-L12 and https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/LiveTestingTypes.fs#L2124-L2128 and https://github.com/WillEhrendreich/SageFs/blob/bba42706/Readme.md#L168-L172
Rough edges: nobody has timed the real save-to-green path end to end, so I'm not quoting a speed. The README says the same thing. Also, if the dependency map hasn't seen the test file that covers your function yet, the narrowing can find nothing (the code comment at LiveTestingTypes.fs L3441-L3452 says so).

### See which lines your tests actually cover, right in the gutter
Before: you guessed, or you ran a separate coverage tool and read a report.
Now: SageFs instruments your project's assemblies with probes, records which probes each test hits, and sends that to the editor as gutter bars. Green means every test covering the line passes, red means some covering test fails, gray means no test reaches it. The same data is how it picks affected tests, by intersecting the changed file's probes with each test's recorded hits. Branch info (fully, partly, not covered) rides along on each annotation.
Why it matters: you see which of your code has no test and which test is failing without leaving the file.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/CoverageInstrumenter.fs#L14-L20 and https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/Features/LiveTestingTypes.fs#L683-L716 and https://github.com/WillEhrendreich/SageFs/blob/bba42706/Readme.md#L405-L415
Rough edges: the first cut of the instrumenter produced invalid IL and ballooned to 39 GB of memory under a full test load. The fix (commit 1bbd235d, in this window) brought it to about 4 GB and added a circuit breaker that turns instrumentation off after 3 failures in a row, so a bad assembly can't take the machine down again. The README lists coverage gutters for VS Code and Neovim only.

### Your agent can run the tests and get an answer it can trust
Before: an agent that wanted to know if your change worked had to shell out to `dotnet test` and parse the output.
Now: there's a `run_tests` tool on the MCP server. It can filter by name, file or category, waits for the result, and hands back a receipt. If the run isn't done when the wait ends, the agent calls again with the receipt instead of polling. A run where something was skipped or never reported comes back as Incomplete, not green. This week's version was simpler (a `timeout_seconds` argument and a poll loop, commit 43e8ed71); it has since been rebuilt around receipts.
Why it matters: an agent can check its own work against your real tests and know whether "passed" means passed.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpTools.fs#L2112-L2130 and https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpRunTests.fs#L1-L30
Rough edges: none I could find that are specific to this window's work, but the timeout version was replaced, so don't describe it as the current design.

### Save a file and the browser reloads, with the app still running
Before: you edited a web app, rebuilt or restarted it, and refreshed the page.
Now: SageFs watches the files you've opted in, re-emits the changed functions into the running session, points the old methods at the new bodies with Harmony, and tells connected browsers to refresh over SSE. The week added the browser side (an injected script and an SSE endpoint) and a Playwright test that drives a real browser through an edit. You choose which files, directories or projects are watched, from the dashboard, VS Code or Neovim.
Why it matters: you edit a Falco handler, save, and look at the page instead of restarting.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/Readme.md#L58-L68 and https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/DevReload.fs#L1-L12 and https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/HotReloadState.fs#L1-L12
Rough edges: it patches methods, so a handler computed once at startup can't be patched and you can't redefine types. An app started with `run_app` gets restarted with your change, not patched in place (about six seconds on the ticker demo, per the README). The details have moved a lot since this week, so link the hot reload doc and not this stretch's commit messages for behavior.

### Alt+Enter in VS Code runs your code, and your Ionide send-to-FSI keys come along
Before: the extension didn't exist.
Now: Alt+Enter evals the selection or the current code block with the result inline, Alt+Shift+Enter evals the file, a "Eval" CodeLens sits above each block, and completion comes from the live session. If you already use Ionide, its send-to-FSI commands (SendSelection, SendLine, SendFile) are rerouted to SageFs, so your existing muscle memory works. It started the week as a TypeScript MVP and was rewritten in F# via Fable on 02-22.
Why it matters: you get a live session in the editor you already have, without relearning keys.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/sagefs-vscode/package.json#L286-L295 and https://github.com/WillEhrendreich/SageFs/blob/bba42706/sagefs-vscode/src/Extension.fs#L2308-L2321 and https://github.com/WillEhrendreich/SageFs/blob/bba42706/sagefs-vscode/src/CodeLensProvider.fs#L1-L10
Rough edges: Alt+Enter replaced Ctrl+Enter on 02-28 (commit 9efd8257), so any docs or videos from earlier in the week show the wrong key.

### Your tests show up in VS Code's own Test Explorer, with pass/fail marks in the file
Before: test results lived in a terminal or the dashboard.
Now: live test results feed VS Code's native Test Explorer, show up as pass/fail marks next to the test functions, and there's a next/previous failing test jump on Alt+Shift+] and Alt+Shift+[. (The 02-24 commit also routed failures into the Problems panel; I didn't re-check that one at head.)
Why it matters: red tests are where you already look for them.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/sagefs-vscode/src/TestControllerAdapter.fs#L26-L35 and https://github.com/WillEhrendreich/SageFs/blob/bba42706/sagefs-vscode/src/Extension.fs#L2939-L2945 and https://github.com/WillEhrendreich/SageFs/blob/bba42706/sagefs-vscode/package.json#L321-L330
Rough edges: the README says client polish still varies across editors, and this is the newest of those clients.

### The dashboard and your editors stay responsive while thousands of tests run
Before: with live testing running about 2,945 tests, the `/api/sessions` and `/api/status` calls started timing out (3 seconds and up) around 40 seconds into a run, because every read queued behind the session manager's mailbox.
Now: reads go to a published snapshot and never wait behind writes. The commit measured 4 to 129 ms on `/api/sessions` and 12 to 150 ms on `/api/status` for the whole run, with zero timeouts over 24 probes in 120 seconds. Dashboard helpers got the same treatment (commit 58aa23e9), and responses are Brotli-compressed on the way out.
Why it matters: the tool doesn't freeze on you in the one moment you most want it, mid test run.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/SessionManager.fs#L214-L232 and https://github.com/WillEhrendreich/SageFs/commit/5cb67321
Rough edges: those numbers are from one run on Will's machine, in the commit message. Treat them as a measurement of that fix, not a guarantee.

### You can see exactly what your session loaded when it warmed up
Before: if a namespace failed to open or a file didn't load, you found out when something later didn't resolve.
Now: the session keeps a record of what warmup did (assemblies loaded, namespaces opened, files scanned, what failed, how long each phase took) and shows it in the dashboard and in a VS Code Session Context view.
Why it matters: "why can't it see my module" gets an answer you can read.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs.Core/WarmupContext.fs#L6-L36 and https://github.com/WillEhrendreich/SageFs/blob/bba42706/sagefs-vscode/package.json#L420-L423
Rough edges: I only confirmed the data type and the VS Code view still exist; I didn't re-check the dashboard panel's current look.

### SageFs starts without Docker
Before: the daemon wanted a Docker-backed PostgreSQL event store. Missing or broken Docker was, in the commit's words, the number one class of user-reported bugs.
Now: the first step this week made persistence opt-in (`--persist`) and defaulted to in-memory, on 02-26. A few days later (03-04, outside this window) the Marten/PostgreSQL dependency was removed entirely and a binary manifest became the only persistence. Today the install is `dotnet tool install --global SageFs` and there's no database to run.
Why it matters: nothing to stand up before your first eval.
Evidence: https://github.com/WillEhrendreich/SageFs/commit/a2665e93 and https://github.com/WillEhrendreich/SageFs/commit/5677d0e2 and https://github.com/WillEhrendreich/SageFs/blob/bba42706/Readme.md#L110-L111
Rough edges: `--persist` no longer exists at the current head, so don't mention the flag as a feature.

### Turn what you did in the REPL into a script
Before: a session's history lived and died with the session.
Now: you can export the active session's evals as an `.fsx` from VS Code (the SageFs: Export Session command) or over HTTP.
Why it matters: an experiment that worked becomes a file you can keep.
Evidence: https://github.com/WillEhrendreich/SageFs/blob/bba42706/SageFs/McpServer.fs#L2850-L2882 and https://github.com/WillEhrendreich/SageFs/blob/bba42706/sagefs-vscode/src/Extension.fs#L2717-L2728
Rough edges: it only exports the active session; for any other session it returns an empty export with a note. The comment above the endpoint also says the endpoint was once documented but never mapped, so both editors' export commands 404'd for a while.
